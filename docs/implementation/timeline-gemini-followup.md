For current live schedule responses, neutral booking is the truthful state. Do not simply repaint all barges/supply boats/test bays with different group colors.

## 2. Timeline layout and interaction contract

- One vertically scrollable timeline viewport, fixed resource rail, sticky month/day header, persistent bottom legend; only the date canvas scrolls horizontally. Sticky z-index layers and group rows cannot cover booked or exception sublanes. A resource row expands to fit its concurrent booking sublanes plus a compact exception rail; the resource identity cell stretches to the same height. Keep stable ordering by start, end, then ID and deterministic lane assignment. Cap extreme stacked height with a clearly labelled `+N more` disclosure that reveals all intervals rather than clipping silently. Empty resources remain scannable.
- Booking blocks show human job/activity, date span, status label and progress if present. Neutral fill/border is the default. Status: in progress = explicit compact label/icon plus a hard progress strip with percentage/accessible name; complete = check and quieter surface; planned = no progress claim. Do not use blue solid fill for in progress. Capacity occupancy bars remain primary-blue quantitative indicators, not vendor colors.
- Exception rail shows maintenance (amber dashed), unavailable (red hatched), and weather (neutral patterned contextual band) with legible label/detail on hover, focus, and inspector. Conflict gets a red warning symbol plus `Conflict` text in detail, anchored to actual intersection days. Respect the backend capacity/approval result; frontend styling does not invent a solver verdict. A booking that intersects an exception stays visible above its own track and shows the exact affected dates.
- Desktop trackpad/native horizontal wheel and scrollbar work without a custom handler. Mouse/pointer drag-to-pan works **only from empty grid/header space**, after a movement threshold; do not steal block click, text selection, scrollbars, vertical wheel, inspector actions, or keyboard focus. Touch uses native pan. Shift+wheel may pan horizontally if it does not hijack normal vertical scrolling. Arrow-key horizontal movement when grid is focused is an accessibility complement, not a replacement for pointer/trackpad. No drag editing or schedule mutation.
- Header controls: previous/next **month** arrows, a labelled month-and-year picker (supports year change), and Today. The selected visible range is explicit; changing month/year updates the API range, today marker, metric denominator, and URL state consistently. Boundary transitions (Dec→Jan, Jan→Dec) work. The canvas can still pan freely inside the loaded range; reaching a range edge offers an understandable way to extend or jump without snapping the user back. Preserve vertical resource position where possible. No misleading one-day arrow with month icon.
- Legend is sticky and contains only meanings actually encoded on the live chart: Booking, In progress, Complete, Maintenance, Unavailable, Weather, Conflict, Today, Selected. Remove the vendor legend/filter from the live view until an explicit API contract supplies vendors. Every hue/pattern has a text/icon counterpart and accessible name. Small blocks retain readable detail via focus/inspector rather than truncation-only labels.
- Mobile uses the existing agenda alternative; month/year controls remain reachable. Do not squeeze the desktop grid into 390 px.

## 3. Synthetic data and live-model boundary

- Preserve fleet-scale v2's deterministic story graph and A-12 golden data. For the next seed revision, make concurrent capacity-valid bookings, one real over-capacity case, booking-versus-maintenance/unavailable intersections, a separate weather hold, standby rows, and cross-page linked decisions easy to find. Do not create artificial group→vendor correlation or any vendor legend. Name dates/reasons so the inspector can explain each exception. Version/checksum the seed; install-if-missing is non-destructive. Local v1→new version replay is an explicit later action, not a development acceptance command.
- Provider selection: `synthetic` is local/preview default; `gemini_developer` is explicit opt-in in local/preview; `vertex` stays the staging/production choice. The same structured extraction schema/validation and state transitions apply. Never silently fall back to synthetic if an explicitly selected live provider fails. Distinguish persisted provenance (`synthetic`, `gemini_developer`, `vertex_gemini`), error, and retry state. No model call on startup, seed, health, opening a page, or background polling; only an intentional extraction action calls it. Keep request timeout and bounded retry/backoff; surface quota/credential/provider errors truthfully to avoid burning a free tier. Ask remains deterministic/read-only unless a separate authorized task changes it.
- Use backend-only secret configuration: `RIPPLE_GEMINI_API_KEY` loaded by `Settings` as a secret and passed to the gateway, plus `RIPPLE_MODEL_PROVIDER=gemini_developer` and an explicit `RIPPLE_INTAKE_MODEL` when opting in. The user-authorized temporary key is **already stored in gitignored local `backend/.env`**. BE-28 must read it only through `Settings` at runtime; agents must not print, inspect, copy, overwrite, commit, or export the key value. They may document variable names/placeholders and append non-secret provider/model settings without disturbing existing `.env` content. Never place the key in `VITE_*`, browser storage, source, seed, tests, docs, logs, URL, or tool output. The key was shared in chat, so rotation is recommended before public-preview use. No automated QA or live call during this development pass. A configured-but-invalid key is a visible provider error, not a green synthetic result.
- Local activation is already prepared in gitignored `backend/.env`: provider is `gemini_developer` and the model ID is `gemini-2.5-flash`. BE-28 must implement those exact setting names and load the file via `Settings` when the backend starts from `backend/`. No Gemini call occurs until a user intentionally starts extraction. Other local/preview installations without the opt-in remain `synthetic` by default; staging/production remain Vertex. The selected model is listed by Google, but access for this particular key is **not verified**; surface a model-access or quota error honestly and do not retry in a loop or fall back silently.
- Pin the official `google-genai` runtime dependency and lock it in a serial dependency step. Preserve the existing Vertex client construction for production. Diagnostics reveal provider/configured state without revealing secret material. No cloud mutation in this goal.
