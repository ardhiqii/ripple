# Preview UX recovery: dense, connected synthetic fleet

Status: approved product direction from the 2026-10-16 screenshot review; development specification, not a claim of completed behavior or browser verification.
Scope: local and synthetic preview only. A-12 golden scenario, production backend default, frozen stack, approval transaction, and scenario isolation remain unchanged.

## 2. Product and data contract

1. The public synthetic preview and local UI landing page (`/` or `/timeline` without `scenario`) selects `fleet-scale` **only when backend scenario metadata advertises it**. The frontend writes the chosen scenario into the URL, sends it via `X-Scenario-ID`, and retains it on every nav, command search, CTA, direct entity link, browser back/forward, and refresh. Explicit `?scenario=A-12-base` continues to open the golden scenario. If fleet-scale is unavailable, choose the advertised A-12 scenario and explain the small golden dataset; never silently synthesize rows. Unknown explicit scenario remains an error, not a fallback. Backend omitted-header default stays A-12 for compatibility. No localStorage-only hidden state.
2. The shell shows active scenario name and a visible `Synthetic data` label. Scenario switch clears the previous scenario's cache and page-specific selection, but preserves a dirty-draft confirmation. A user can always tell whether they are in Fleet-scale or A-12. Demo Lab explains the difference and links to each scenario without losing context.
3. Fleet-scale v2 is a *coherent story graph*, not only a larger row count. Target 20–24 resources across barges, supply boats, test bays, and lift crews; 40–50 jobs; 90–110 bookings over at least 28 days; 35–45 readiness items; 25–35 events; 10–12 immutable decisions. Deterministic IDs/times/checksum, no runtime randomness. If a target cannot fit the existing schema, document the exact constraint and retain at least the already declared v1 counts rather than inserting invalid records.
4. Curated cases must coexist in the same scenario: (a) busy barge with multiple adjacent jobs, (b) one empty standby row, (c) maintenance and unavailable intervals on different resources, (d) visible booking conflict and over-capacity, (e) supply-boat dependency, (f) stale/low-confidence readiness, (g) ready readiness item with a persisted source, (h) extracted event awaiting review, (i) needs-clarification event, (j) active/failed run, (k) options-ready plan including infeasible option, (l) approved, rejected, and reply decisions. At least six real event→run→plan→decision links and cross-page job/resource references resolve within the scenario.
5. Human-readable synthetic names and source messages convey operational meaning (vessel, task, cause, date) without imitating real customer data. Avoid strings like `Fleet-scale synthetic event 07` as a prominent title. Raw IDs and versions remain available as secondary audit metadata/copy actions. Baseline decision timestamps and scenario epoch make records visible in the appropriate date window.
6. Version the new seed and checksum. Install-if-missing never overwrites a tester's edited scenario. A v1 database can be upgraded only through an explicit, scenario-scoped reset/reinstall action with confirmation and a clear warning; do not auto-reset shared preview or A-12. Keep the existing CLI's explicit `--scenario` guard and transactional scenario isolation. Do not run a reset during this docs-only planning phase.

## 3. Shared UI grammar and action semantics

- Reuse the existing design-system tokens, Phosphor icons, customized shadcn primitives, and light theme. Primary blue represents navigation/focus/action, not vendor, status, or a generic metric fill. The earlier Baker/Powerlift/Schlumberger fixture palette is valid only where a real vendor assignment exists; the later [Timeline follow-up](timeline-gemini-followup.md#1-evidence-and-decisions) supersedes vendor-color rules for live `/schedule`, which has no vendor field. Status is conveyed separately by text/icon/pattern. No arbitrary new page palette, gradient-as-data, second component system, or broad CSS rewrite.
- Page headers share a title, one-line task description, scenario context, and at most one prominent creation action. Summary values are plain tabular numbers with an explicit scope (`Entire scenario`, `Filtered result`, or `Visible range`); remove colored rectangles behind isolated numerals. One panel depth is enough: avoid nested bordered cards and browser-default-looking boxed links.
- Link text describes the destination; button text describes the action. A row click inspects; a mutation uses a distinct labelled button with pending/success/error feedback. Never make a checkbox perform a destructive or status-changing action unless the label and interaction clearly say so. No `#` links or dead/disabled teaser controls.
- Format dates relative to the scenario epoch for schedule (`D+n` with a readable calendar-date tooltip/secondary text), audit timestamps in locale with timezone, freshness as `Just now`, `25 min ago`, `3 h ago`, `2 d ago`, or `Unknown`; cap numerical precision. `Stale` is not a numerical age. Show exact source time in detail when relevant.
- All sheet headers use a human title plus status. IDs and versions are secondary copyable metadata. A sheet has one primary action and an obvious close/back path; no duplicate Close controls. Loading, empty, error, pending, conflict, and no-results states keep the same surface grammar and explain the next valid action. Focus returns to the invoking row on close; selected/focus rings never recolor the domain block itself.
- At 1366×768, toolbar and primary navigation remain one line; dense tables remain readable, with horizontal overflow only within the table/workspace. At 390×844, use readable stacked rows or agenda; no clipped primary actions. Defer visual/browser verification until QA, but implement responsive source now.

## 4. Page contracts

### 4.1 Timeline

- Fleet-scale landing has enough resource groups/rows and bookings to need vertical scrolling. Keep the resource rail and day header sticky inside the two-axis timeline viewport and the legend persistent at the bottom; do not make the whole page a giant empty fixed-height chart. Sparse A-12 uses content-fit height and a clear `Golden A-12 · 2 resources` context, not fabricated fleet rows.
- Group bars show group name, resource count, and correctly scoped planned-load percentage. The metric strip computes from the visible range and eligible capacity; click filters only if implemented, otherwise metrics are static indicators. Search, group/status filters and date controls affect real API-backed rows, not just block opacity. A vendor filter is hidden until a typed live vendor contract exists. The date range, today marker, maintenance/unavailable, conflict and occupancy treatment are meaningful and use the established palette, as amended by the [Timeline follow-up](timeline-gemini-followup.md#2-timeline-layout-and-interaction-contract).
- A booking click opens a job inspector; Readiness and Changes deep links open the same job/context. Closing inspector clears `job` URL state and restores focus. Empty resource rows, overlapping jobs, and maintenance remain visible and distinguishable.

### 4.2 Readiness

- Default fleet view is a work queue, not a spreadsheet of raw IDs. Lead each row with job/stage and readable task; show risk/status, required day, ETA, effective slack, freshness, confidence, and a clear `Review` action. Secondary raw item ID is copyable in detail. Group headers and summary counts state whether they are scenario-wide or filtered. Stage names turn `function_test` into `Function test`; never render snake_case as user copy.
- Remove the bare status checkbox from the table. `Review` opens an item detail sheet. The sheet explains source, stale/low-confidence signal and current status; `Mark ready`/`Reopen` is an explicit server PATCH with expected row version. Pending affects only that item; success shows new status and refetches summary/list/detail, failure restores prior state with a reason. If an item cannot be marked ready (waived/blocked/invalid), explain why rather than showing an ambiguous disabled checkbox.
- Preserve selected row/scroll position while the mutation settles; do not move it to another group in mid-click. `Open job` goes to Timeline with `scenario` retained, correct date window and selected job. `Find items from this source` uses a real server-backed filter/query. If there is no bulk action, there is no selection checkbox.

### 4.3 Changes and event detail

- Inbox rows prioritize cause/meaningful source summary, linked job(s), human lifecycle, updated time, and one next action. The summary strip uses server scenario-wide lifecycle counts separately from filtered count. Filters/search are server-scoped and show clear-result behavior. Show 25+ events in fleet-scale with pagination or intentional list scrolling; no full UUID as the visual headline.
- Both row click and `Continue` open the **same canonical event detail** at `/changes/$eventId` (or one URL-backed sheet bound to that route). Do not stack a separate intake and preview sheet for the same event. The detail presents one clear progression: Source → Extraction → Investigation → Plan/decision, with current step and next valid action. Source text, extracted fields, job links, run status, plan link, and immutable decisions are server-backed.
- After `New change`/`Run sample` submit, keep the new event in the same detail context. Backend extraction completes or fails truthfully; while pending, show bounded progress and automatic revalidation/polling with manual Retry, not an endless `Refresh extraction status` as the only path. On completion, the same detail transitions to review/correct extraction. `Structured` appears only when an extraction version exists. `Needs clarification` shows missing fields and correction action. A provider/config failure offers a truthful retry or explicitly labelled deterministic local-preview path; it must never masquerade as a Gemini result.
- Starting investigation requires a persisted valid extraction, registers the server run, and links to the resulting plan. The existing approval transaction remains the only schedule-writing path. Direct event links load even if the item is not on the first inbox page. Closing returns to the filtered inbox; browser back/forward preserves scenario.

### 4.4 History

- Fleet-scale default shows persisted decisions and meaningful action mix; A-12 can be truly empty until a decision is made. Summaries are scenario-wide, while filtered result count/pagination is distinct. Show cause, action, job, actor, recorded date, and schedule-version transition; UUID/plan ID is secondary. Do not render five large zero-cards and an oversized blank state for a populated fleet.
- Filters, date window and cursor pagination operate on server results; clear filters stays in scenario. Detail is immutable, links to event, plan audit, and Timeline job. A-12 empty state explains the golden scenario and offers a scenario-preserving `Explore fleet history` link; `Open Demo Lab` must also retain scenario. No plain `<a href="/demo">` that drops root search state.

### 4.5 Shared cross-page flow

The primary rehearsal: Fleet Timeline job → Readiness item/source → Change event → extraction review → investigation/run → plan option → approve/reject/reply → Timeline change and Decision History audit. Every link carries the active scenario and canonical entity ID. A second rehearsal: History audit → source event → plan audit → Timeline job; all records agree on IDs, versions, dates, and human labels. `Ask Ripple` is read-only and may reference current scenario entities; it must not bypass the approval transaction. Demo Lab can reset only the selected synthetic scenario with explicit confirmation. Implementation does not claim these rehearsals passed until later E2E/browser QA.

## 5. Execution and parallelism

New bounded packets: `BE-25` extraction completion, `BE-26` fleet-scale v2 story seed, `INT-20` scenario landing/continuity, `FE-26` Timeline density, `FE-27` Readiness clarity, `FE-28` Changes flow, `FE-29` History, then root-owned `INT-21` integration. The packets' Allowed files are exclusive write reservations; one task ID per worker. Existing FE-15–FE-25 / BE-16–BE-24 / INT-10–INT-19 remain historical `dev_done / QA pending`; do not reimplement them.

Concurrency is real overlap, not `spawn; wait; spawn; wait`. Root first inventories and reserves files, then dispatches **two ready disjoint writers before waiting**. While they work, root performs read-only diff/contract review. On the first worker completion, review its diff and immediately refill the free writing slot with a ready disjoint task; do not wait for the other worker unless its contract is a prerequisite. Only then wait for a relevant completion. Maximum two writing subagents; root does not become a third writer during a two-writer wave. Keep a simple in-turn ledger of `blocked/ready/active/integrating/dev_done` and file reservations.

Suggested overlap: `BE-25` + `BE-26` may run together only with BE-25 owning event service/route and BE-26 owning seed builder/CLI (no shared file or mutable database command). INT-20 shell/scenario routes and FE-27 Readiness may run concurrently because their files do not overlap and the scenario contract is already frozen in §2. FE-26 and FE-29 can overlap; FE-26 exclusively owns the existing timeline selectors in `styles.css` during its assignment, and FE-29 cannot touch that file. FE-28 waits for BE-25's extraction contract and owns Changes files; it can overlap FE-29 if FE-29 is still pending. `INT-21` begins after all page writers, with one root writer for shared styles/contract integration. If a writer needs a reserved/shared file, it reports the exact path and pauses that subchange; root reassigns only after current owner completes. No parallel seed/reset, migration, OpenAPI generation, package install, test snapshots, or shared global stylesheet edit.

Development phase remains docs/implementation/README.md §4.8: implement code, inspect source, then root-only static/build checks. No test-file work or test runs now, no browser walkthrough, no deploy/cloud mutation. Later INT-14–INT-16 E2E/browser QA should rehearse the two flows above, sparse A-12 versus dense fleet, pagination, mobile/sticky scrolling, reset/replay, and real failure states; the user will authorize that phase separately.
