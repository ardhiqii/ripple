# Timeline issue and weather clarity

Status: historical development specification with FE-34/FE-35/INT-24 source present; browser QA is **not** claimed here. The newer [grid-annotation pass](timeline-grid-annotation-pass.md) supersedes this document's issue-tint/badge placement, hidden-booking disclosure, and weather-header placement only. Its data truth, API, seed, approval and other-page boundaries remain in force.

## 1. What is wrong, and what the data means

| Evidence in current UI/source | Correct interpretation and required correction |
|---|---|
| `CalendarHeader` renders `WeatherContextMarker` whenever `day.weather?.length` is nonzero. The screenshot consequently has a cloud under almost every date. | `go=true` is an ordinary observation, not a warning. Only a `go=false` observation earns a persistent weather no-go indicator. Unknown `go` remains context, not a warning. Other observations remain in the schedule data and mobile agenda; do not invent a new desktop weather-inspection control in this pass. |
| `TimelineIssueMarker` uses `gridColumn` for the first day of a contiguous cluster, while the visual range is only a 2px line. The 24px trigger floats at the edge of a 16px marker band. | Issues are **day-granular and resource-scoped**. A multi-day issue must visibly occupy precisely its resource × affected-day cells; the badge must visibly belong to that range and not seem attached to a neighbouring day. Do not imply hour precision. |
| A `+2` badge is rendered when two active issue records overlap. Its CSS unconditionally uses danger red, while native `title={label}` opens a long black browser tooltip in addition to the custom tooltip/dialog. | `2` is the number of distinct issue records in that resource/date cluster, not a severity score. Use the most severe active issue for the badge treatment, reveal all kinds in the detail, and remove duplicate native `title` tooltips. One short custom tooltip and a click/tap detail are enough. |
| Legend says `Weather` and `Exception marker`, with no location/scope explanation. | Legend must distinguish day/location context, resource/day issues, bookings, Today and selection. It must match only visible encodings and explain `2 issues`/mixed kinds without color-only meaning. |

Source anchors: `frontend/src/components/timeline/timeline-workspace.tsx` (`CalendarHeader`, `WeatherContextMarker`, `ResourceRow`, `buildTimelineIssues`, `clusterTimelineIssues`, `TimelineIssueMarker`); `timeline-density.css`; `timeline-legend.tsx`; `features/schedule/types.ts`. Current API has weather `day/location/metric/value/go/source`, explicit resource unavailability, and exact capacity-overflow days. No backend/API/seed change is needed for this presentation pass.

Reference principles: [SAP Calendar](https://experience.sap.com/fiori-design-web/calendar/) distinguishes highlighted days with a consistent legend; [SAP Planning Calendar](https://experience.sap.com/fiori-design-web/planning-calendar/) distinguishes resource rows and appointment/day meanings; [SAP Calendar Card](https://experience.sap.com/fiori-design-web/calendar-card/) uses different legend shapes for highlighted days versus appointments. [W3C tooltip pattern](https://www.w3.org/WAI/ARIA/apg/patterns/tooltip/) supports hover/focus and Escape; interactive links belong in a click popover/dialog, not a tooltip. These are guidance, not a request for a calendar library.

## 2. Frozen UI contract

### 2.1 Visual hierarchy and geometry

1. Keep the existing sticky resource rail, sticky calendar header, persistent bottom legend, 2-week/Month control, horizontal pan, neutral live bookings, and approximately **68–72px one-lane resource rows**. Issue presentation must not increase normal row height or add a second exception lane. Two true concurrent bookings may still grow the row under the previous contract.
2. For each resource, derive a view model keyed by **absolute scenario day**. Each day has its active explicit maintenance/unavailable intervals and exact `conflictDays`, unique by stable issue ID. Keep identity, reason, impact and linked job IDs; do not infer a resource issue from weather or from a whole booking whose conflict is only one day. Out-of-range days are clipped to the visible canvas without changing their original inclusive dates in detail.
3. Put a **very light day-cell tint in the compact marker band** for resource days with active issues. The band is part of the same day grid as the header/bookings. It may include a 2–3px leading or lower-edge accent; do not tint a full canvas column for a single resource's issue, recolor a booking, or obscure its label/progress/selection. Exact affected days only; normal days stay neutral. Adjacent cells with the same issue set may join visually into one restrained continuous segment, but day boundaries stay discernible. A no-issue row does not display an empty rail or decoration.
4. At the **first visible day cell** of each contiguous run with the same issue set, put one compact badge inside that cell's marker band, centered on that day's column rather than hanging across a grid line. The subtle segment fill/rule continues through every affected day; the badge never extends the range or shifts its start. A run crossing an offscreen edge remains legible when panned. At 2-week and Month day widths, prefer a 20–24px pointer/keyboard target while preserving the 16–18px band and booking click area. Do not increase all rows or place an invisible overlay over a booking just to hit a numeric target.
5. One active issue: show its kind icon (maintenance wrench, unavailable blocked, capacity conflict warning). Multiple: show `2`/`3` count with a stack/issue icon or `+2` if required by available width. **Count means distinct active issues**, and accessible text must say e.g. `2 issues on Fleet Barge 2, 16–17 Oct`, not an unexplained `+2`. Visual priority: unavailable/capacity conflict → danger; maintenance alone → warning. When both danger and warning exist, show the danger treatment plus count; do not combine red/amber gradients. Distinguish unavailable from conflict by icon/detail/pattern, not a new hue. Never mark valid parallel bookings as a conflict.
6. Keep day-date digits and weekday text visually primary. In the header, render a quiet no-go-weather marker **only where any `go === false`**. If multiple locations are affected that day, show one marker and list the locations in detail. `go === true` or unknown never creates a warning icon. No-go weather is location/day context, **not** a resource unavailability or automatic capacity-zero claim. Where matching-resource context is useful, at most a faint date-cell hint on matching resource rows; do not shade all resource rows or steal the issue badge. Do not show weather as a booking/maintenance chip.
7. Use existing design-system tokens: neutral canvas/bookings, primary blue only for selection/Today/action, warning amber for maintenance, danger red for explicit unavailable/conflict, muted slate for routine context. Low-opacity tints must preserve grid/date/booking contrast. Use shape/icon/pattern and words as well as color. Keep Phosphor icons and one consistent stroke weight. No decorative gradient and no fabricated vendor coloring.

### 2.2 Detail, accessibility and legend

1. Hover **or keyboard focus** on an issue badge shows a short, styled tooltip: `2 issues · Fleet Barge 2 · 16–17 Oct`. No native `title` attribute on custom markers. Do not put paragraphs or actionable links in the tooltip. Avoid tooltip/dialog duplication while the detail is open.
2. Click/tap/Enter/Space opens a stable detail anchored inside the viewport, with resource name/location, **inclusive date range**, issue count, each distinct kind + reason + impact, linked job actions, and a clear close. Escape/outside click closes, focus returns to trigger, and the detail does not clip behind sticky rail/header/legend or the scroll container. Use the project's existing popover/dialog primitive if possible; a portal is acceptable if needed for clipping. Hover is never the only way to read an issue.
3. No-go weather opens a similar compact date-context detail with affected location(s), observed metric/value, `No-go` meaning, and source. Do not imply it changed capacity. Routine `go=true` values remain in schedule data/mobile agenda but need no persistent desktop header icon; do not create a dead date control merely to expose them. If a date has multiple weather observations, summarize without multiple overlapping icons.
4. The persistent legend needs scannable groups/visual separators: **Schedule** (`Booking`, `In progress`, `Complete`, `More bookings` when shown); **Resource issues** (`Maintenance`, `Unavailable`, `Capacity conflict`, `2 issues`); **Day context** (`Weather no-go`, `Today`, `Selected`). The exact displayed entries must match the app's actual states; drop `Exception marker` and generic `Weather`. If space is tight, the legend itself can horizontally scroll without scrolling the timeline; groups and labels must remain understandable at 1366×768 and in the mobile agenda. Do not rely on the legend as the only explanation: marker tooltips/details name the semantics.
5. Preserve booking click → Job Inspector, related-job action → same inspector, existing filters/search, URL and pan, collapsed groups, and mobile agenda. A marker click must not trigger pan or a booking selection underneath. A valid `go=true` observation must not imply an issue. Selected/focus outline is primary blue and separate from issue severity.

### 2.3 Examples for deterministic visual review

| Case | Expected visual and detail |
|---|---|
| Barge 2 has maintenance and overflow on 16–17 Oct | Only Barge 2 issue-band cells for 16–17 Oct have subtle danger-priority treatment. One count badge begins **inside 16 Oct**; the segment continues through 17 Oct. Detail lists maintenance and capacity conflict with exact dates and linked job. Other barges' cells are uncolored. |
| Barge 1 has maintenance only on 20 Oct | One amber wrench on 20 Oct and only that resource/day is softly marked. |
| Overflow is on 17 Oct within a booking spanning 15–19 Oct | Only 17 Oct is marked as a conflict; booking remains neutral, with precise underline/inspector context from the existing contract. |
| Routine `go=true` weather on every day | No parade of clouds. Dates and weekdays remain readable; data is still accessible from the date context/agenda if the existing interaction supports it. |
| No-go on 21 Oct for West Alpha only | One no-go icon in the 21 Oct header. Detail names West Alpha and source. No claim that resources in other locations have a hold; no capacity-zero inference. |
| Two issues end at a month boundary; user pans Oct→Nov | Grid-day alignment, first-visible marker, date range, sticky header/rail and focus remain correct; no duplicate badge at the same boundary. |
