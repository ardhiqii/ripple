## 2. Frozen layout contract

### 2.1 Resource-day issues: background first, icon second

1. Retain the current left sticky rail, month/date sticky header, bottom legend and dense row. One booking lane remains approximately **68–72px**, including the existing 16px annotation band; do not add a new issue row or enlarge the default resource row. Booking lane count may grow only for actual concurrent bookings or deliberate expansion.
2. For each resource and absolute day, derive a set of **distinct active issue IDs** from explicit `maintenance`/`unavailable` intervals plus the exact `conflictDays` of bookings. Clip to the visible buffered canvas but keep original inclusive dates for details. Do not infer an issue from a `go=false` weather observation. Do not mark an entire job if only one date overflowed. Filters must not hide a real resource issue or its job link.
3. The whole resource-day **track background cell**, not only its 16px footer, gets a restrained tint, still leaving the gridline visible. Use exactly one tint per cell: `unavailable` or capacity `conflict` wins as danger; otherwise `maintenance` uses warning. Mixed danger+warning stays danger, never a red/amber gradient. Existing weekend/selected-period/today treatments retain their meanings. The issue tint stays behind the neutral booking block, its text/progress and selected focus ring. Do not tint the global date column or other resources.
4. Each affected contiguous run has a 2px rule at the bottom of the resource's issue band from **first through last affected day**, clipped to canvas. A small 12–14px inset icon or numeric count sits wholly **inside the first affected day cell** and the 16px band; no negative margin, 24px circle, or baseline crossing. If one issue spans multiple days, one icon at the first visible cell plus the tint/rule across the range. If two+ issues overlap, use one numeric `2`, `3` etc. for the distinct active records. If the set of active issues changes mid-range, split the run and recompute severity/count for each run. No blank decoration on issue-free dates.
5. The entire tinted day/segment may be the issue-detail trigger **only in the unoccupied annotation band**; booking blocks retain their own click targets. Provide one clear focusable trigger per run with an accessible name: resource, issue kind/count, inclusive affected dates. Hover/focus gives concise tooltip; click/tap/Enter opens the existing stable detail with each reason, impact and linked job; Escape/outside closes with focus return. If the icon is visually tiny, expand the trigger horizontally *within that run's annotation band*, not vertically over a booking or into a neighbouring day. Keep portal positioning/scroll handling from FE-34. Do not rely on color alone: icon/count, tooltip, detail and legend carry meaning.
6. Source example: Barge 2 has maintenance and overflow on 16–17 Oct, and maintenance continues on 18 Oct. Barge 2 cells 16–17 get one pale danger tint, `2` at the center of the 16 Oct annotation cell and a range rule through 17 Oct; 18 Oct switches to pale warning with a wrench inset in its own cell. Barge 1 and date header remain neutral. No indicator may float into Barge 3's row.

### 2.2 Hidden bookings: date footprint plus stable expand

1. The old `hiddenBookingCount = bookingLanes.filter(lane >= 2).length` and single `disclosurePlacement` are not enough. Create a pure, deterministic per-day visibility layout for the buffered canvas: at each absolute day, choose at most **two** visible active booking IDs; all other active IDs are hidden **on that day only**. Prioritize a selected job if active, then already-visible continuing jobs for continuity, then `in progress`, then earlier start, then stable ID. No randomly changing order. When a booking is hidden on only part of its duration, it reappears when a visible lane frees; render only its visible fragments and retain the original job ID/range in inspector. A continuation fragment uses a subtle cut-edge/continuation cue, not a fake new booking.
2. Collapse mode renders those at-most-two visible fragments. Group hidden **resource × day** occupancy into contiguous segments where one or more booking IDs are hidden. At the bottom edge of the **last visible booking lane**, show a neutral slate 2–3px horizontal rule on those days only; no floating pill, row-spanning overlay, or blue selection-like color. Segment tooltip/focus text may say `2 hidden bookings · 21–23 Oct`; the rule itself need not be a tiny click target. If counts/sets change over a run, split the segment or state the exact per-day count in detail. Do not claim these are conflicts; capacity-valid parallel work may be hidden purely for visual density.
3. The sticky resource cell gets a compact text button under resource code/name: `+N hidden bookings` in collapse mode and `Show fewer` in expanded mode. `N` is the number of **distinct booking IDs hidden at least once in the selected period**, not the sum of per-day counts and not the number of bookings in the entire three-period buffer. The control's accessible name also states the selected-period inclusive dates. If no hidden booking falls in the selected period, do not show a stale `+N` button; occupancy lines in buffered adjacent dates can still appear when panned there, and the period/URL changes when the pan settles. Leave resource utilization visible. A button in the rail remains stationary under horizontal pan, so the meaning is not anchored misleadingly to one date.
4. Click/Enter/Space on that control expands **this resource only** to show all its bookings in the selected/visible canvas using stable non-overlapping lanes; no silent cap on the expanded row. The button becomes `Show fewer`. Preserve vertical scroll anchor/resource identity so expanded content does not jump offscreen, and keep the left rail exactly the same height as its track. Collapse restores the compact two-lane presentation, focus and selected job. Do not reset expansion on a simple horizontal pan unless the resource/scenario changes; no drag editing or schedule mutation.
5. When a resource has both issue and hidden-booking occupancy on the same dates, tint the resource-day cell and keep its inset issue marker/range in the 16px annotation band. The neutral hidden-booking rule remains at the booking-lane edge, visually separate. If the row is expanded, remove the hidden-booking rule because nothing is hidden. The “More bookings” legend swatch must match the neutral line and `+N` rail control; it is not a warning/conflict.
6. Example: Test Bay 4 has four distinct hidden bookings whose intervals fall across 22–30 Oct. The rail reads `+4 hidden bookings`; a neutral line appears only over the actual hidden-day segments, not merely 22 Oct. On expand, all original bookings become visible on their dates, rail says `Show fewer`, and the line disappears. A job that stops being hidden on 27 Oct is visible again from 27 Oct, rather than remaining absent until its original end.

### 2.3 Date/weather header and responsive behavior

1. Keep date-cell width/grid alignment identical to resource-day columns in both `2 weeks` and `Month` modes. Within the existing roughly 52px date-header cell, use **three explicit rows**: number (including Today circle), weekday, weather. The no-go marker is **in flow below weekday**, centered or left-aligned consistently across dates. Target 10–12px weather icon plus `No-go` at normal desktop width, restrained warning color/pattern distinct from the blue Today marker. If label does not fit a narrow slot, show the icon alone with a full accessible name/tooltip. Do not grow the header to 90px just to fit an icon.
2. Only `go === false` observations create the weather row content. Multiple no-go locations on the same date share one marker; click detail lists each affected location/metric/source. `go=true`/unknown remains data context, not a persistent alert. No-go is not automatic capacity-zero or resource unavailability; preserve that existing business boundary. No weather icon can cover the weekday or the next cell's date at 1366px or a narrow mobile view.
3. The mobile agenda stays a separate readable list; no desktop grid-only affordance becomes the sole access path. Keep today, no-go and booking/issue distinctions accessible by keyboard/tap. At 1366×768, preserve a useful search field and visible horizontal scrollbar; sticky rail/header/legend and portals must not clip or occlude controls. Use current design tokens, Phosphor icons, tabular numbers and compact typography; no second UI system, raw palette, gradients, or new dependency.
