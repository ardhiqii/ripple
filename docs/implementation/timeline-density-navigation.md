# Timeline density and continuous navigation recovery

Status: approved **design/development specification** from the latest 2026-10-16 screenshot review; no implementation, DB replay, or browser QA is claimed by this document. Applies to the local/synthetic-preview Timeline. Previous FE-30/FE-31 and INT-22 source is preserved as the starting point, not re-run as a whole. This document supersedes only the Timeline row-height, exception presentation, and horizontal-horizon clauses of [Timeline/Gemini follow-up](timeline-gemini-followup.md); Gemini provider, seed isolation, approval boundary, and other pages are unchanged.

## 1. Evidence, user intent, and references

| Screenshot finding | Current source evidence | Required outcome |
|---|---|---|
| A barge with one booking occupies ~200 px and the resource name floats in a tall empty cell. | `ResourceRow` packs each exception and conflicted booking into separate 28 px rail lanes, then sums those lanes with 52 px booking lanes for `rowHeight` (`timeline-workspace.tsx`). | Normal resource rows stay compact. Only genuinely simultaneous bookings add height; exceptions never each add a full row. Keep sticky resource cell and date canvas exactly aligned. |
| One-day `Weather` and maintenance pills are truncated and look like bookings. | The current exception chip is 22 px high with 7 px text and ellipsis inside a 48 px day. Weather observations are copied to every matching resource and converted to unavailable intervals (`schedule-adapter.ts`). | Use compact, date-anchored **icons/markers** with full hover, focus, and click detail. Shared weather is shown once per affected location/day in date context, not as repeated task-like cards. Do not claim a weather observation sets capacity to zero unless an explicit backend unavailability interval says so. |
| `Conflict` can cover an entire booking even if only one day overflows. | Adapter flags all booking IDs whenever a resource report has any overflow; current marker uses the whole booking span. | Derive affected days from capacity points with `overflow > 0` and their booking IDs; mark those day segments only. A booking-level warning may summarize them, but its detail lists the exact dates. Capacity-valid parallel bookings are not conflicts. |
| `Month and year October 2026` accompanies `13 Oct–11 Nov`, search is clipped, and pan ends at the fetched range. | Toolbar keeps a visible long picker label and full range in a nowrap row. Reference principles, **not** a library adoption: [SAP Planning Calendar](https://experience.sap.com/fiori-design-web/planning-calendar/) shows named resource rows, time-scale switching, reduced-height appointments, and concurrent appointments stacked; [SAP Single Planning Calendar](https://experience.sap.com/fiori-design-web/single-planning-calendar/) caps dense stacks with `More`; [FullCalendar resource timeline docs](https://fullcalendar.io/docs/timeline-view) show selectable week/month horizons, minimum slot width, maximum stack and two-axis scrolling. Ripple keeps its custom CSS Grid; no FullCalendar/Gantt dependency. [WAI-ARIA tooltip pattern](https://www.w3.org/WAI/ARIA/apg/patterns/tooltip/) informs hover **and keyboard-focus** detail with Escape dismissal; interactive actions belong in a click popover/inspector, not inside a tooltip. These are design references, not claims of completed QA.

## 2. Compact row and exception contract

1. Baseline resource row target **68–72 px** at desktop: one 42–46 px booking track plus one integrated 14–18 px marker line, border/gap included. A resource with no booking uses the same compact row, with a restrained empty state. A simple maintenance, weather, or conflict marker never increases row height. Booking and exception visuals must not obscure each other. The left sticky resource cell stretches to the exact same computed height as the right canvas; keep resource name/capacity vertically stable at the top/center rather than centered in a 200 px void.
2. For actual simultaneous bookings, show at most **two visible booking lanes** by default. Height grows only for those lanes (roughly 108–120 px total), not for every exception. When a third or later booking is simultaneous in a date cluster, show a date-anchored `+N bookings` disclosure that opens a popover or focused expanded row with all IDs, ranges and links. Expanding is deliberate and reversible; non-overlapping sequential bookings reuse the first lane. Never silently hide appointments. Capacity 2+ can make concurrency valid.
3. Replace the large exception rail with a **single compact marker band**, aligned to the same day grid. Maintenance: wrench icon + thin amber dashed range line. Explicit unavailable interval: blocked icon + thin red hatched range line. Conflict: red warning icon at each actual affected day or contiguous overflow segment, and a subtle underline on the corresponding booking segment. Different issues on one day cluster into a `+N issues` marker rather than stack vertically. Each marker has an accessible name with kind, resource/location, inclusive dates, reason, and impact; hover/focus shows concise tooltip, click/tap opens a stable detail popover with all issues and related job links. Escape closes and returns focus. Icons retain readable 20–24 px trigger targets even when one day column is narrow. The marker band and legend use icon+word/pattern, not color alone.
4. Weather from `ScheduleResponse.weather` is **location/day context**. Keep it typed separately in the frontend schedule adapter; do not infer weather by searching an unavailability reason string. Show one weather indicator per affected location/day in the date header or a narrow shared contextual band. If all resources share one location, show it once; if multiple locations, indicator/popover lists affected locations and the grid may use a subtle day shading only on matching resource rows. `go=false` is a weather no-go signal, not automatically a persisted resource unavailability or capacity-zero interval. Only explicit `/schedule.unavailability` may use unavailable styling and capacity semantics. Popover explains what the signal means and its source.
5. Booking block remains neutral because live API has no vendor identity. Preserve status text/icon, progress, selected/focus semantics, job inspector and approval-only mutation path. Conflict is precise and does not recolor the entire neutral booking red. Maintain reference-like 1D horizontal bars across dates but do not copy the supplied reference's vendor palette without vendor data.
6. Keep group headers slim, resource rail sticky, date header sticky, bottom legend persistent, vertical scroll position stable. No sticky group or tooltip layer may clip markers or cover neighbouring bookings. The legend includes only encodings truly rendered; a long legend can scroll horizontally independently rather than reducing chart height.

## 3. Horizon, date state, and horizontal pan contract

- Provide two explicit controls: **2 weeks** (rolling 14-day detail, default) and **Month** (calendar-aligned month overview). A selected October view must not silently mean 13 Oct–11 Nov. The first seeded month may be partial because scenario day zero is 13 October; label it `Oct 2026 · from 13 Oct` and show the exact inclusive range. Subsequent months use their real 28–31 days. `Today` goes to the scenario's actual today when in horizon, otherwise a clearly labelled `Scenario start`; no fake current-day marker.
- Previous/next buttons move by the **active horizon**: 14 days in 2-week mode, one calendar month in Month mode. Accessible names and tooltips say `Previous 2 weeks` / `Next 2 weeks` or `Previous month` / `Next month`. The month/year picker jumps to a calendar month; before-scenario months are disabled with explanation, while future months can be loaded even when there are no bookings. Do not cap navigation at the last day returned by the current API response. Keep a bounded configurable horizon, e.g. 12 months of synthetic preview, with an explicit end state rather than silent failure.
- **Direct horizontal pan remains primary.** Native trackpad/scrollbar, mouse drag on empty grid, touch pan, and keyboard scroll must work. Display a bounded **three-period buffer** (previous/current/next 14-day or calendar-month period); fetch the buffer from `/api/v1/schedule?from=&to=`. When panning near an edge, request the adjacent period and preserve the calendar date under the user's viewport instead of snapping back. Do not render a full year eagerly. Panning a few pixels does not refetch; period crossing or near-edge prefetch does. Preserve vertical position, selected job, filters, and inspector. Do not steal booking click, marker click, vertical wheel, text selection, or browser back/forward. No drag editing.
- URL is canonical: retain `scenario`, `job`, search/group/status filters; add a typed `horizon=2w|month` and keep inclusive absolute scenario-day `from/to` as the **selected period**, not the three-period buffer. A toolbar jump and a settled horizontal pan update this URL; direct links/refresh/back-forward restore mode and anchor. Legacy `from/to` links without `horizon` open in 2-week mode around the provided start rather than silently losing the job. Reject or clamp malformed/reversed dates visibly. Scenario switch resets an invalid period to that scenario's start and preserves isolation.
- Separate `selectedPeriod` from `canvasRange` in code. The route fetches a buffered `canvasRange`; App metrics use only `selectedPeriod` and label denominator `Selected period`. CalendarHeader and block placement use `canvasRange`; the viewport is initially anchored to `selectedPeriod.from`. The workspace exposes one stable `onAnchorDayChange(absoluteDay)` callback on settled pan, not on every pointermove. In Month mode, crossing into an adjacent calendar month selects that month; in 2-week mode, crossing a 14-day boundary selects the adjacent rolling period. The route derives a new buffer and refetches only when the selected period leaves the current buffer. Keep `Today`, group counts, conflict locations, and metric bars aligned to the selected period.
- The date adapter must not render or allocate all intervening day columns from day zero merely because a user jumps 11 months ahead. API data remains absolute day indexed, but the canvas day list is built only for the buffered range with an explicit offset; date, booking, unavailability and weather placement all use that offset. A month/year boundary and leap February behave correctly in UTC calendar-day math. Empty future periods show resources with `No activities in selected period`, not a broken blank canvas.
- Toolbar at 1366×768: keep title/context, search, essential filters, horizon switch, date jump and compact range legible. Replace the verbose inline `Month and year` text with a compact picker trigger that has a visible short month/year label and full accessible name. Do not duplicate the entire range beside it in Month mode; 2-week mode may show a concise `13–26 Oct` secondary range. Move nonessential filters into one labelled Filters popover or a second aligned toolbar row when width is constrained; never truncate the search to an unusable field or let controls overlap. At 390px mobile, use the existing agenda with accessible horizon controls.

### Frozen workspace integration interface for parallel workers

`FE-32` owns the Workspace side: receive `canvasRange`, `selectedPeriod`, `dayWidth`, and `onAnchorDayChange(dayIndex)` as typed props; render only buffered days and emit a **settled** absolute day index without mutating URL/API data itself. `FE-33` owns the route/App/toolbar side: derive these props from URL and scenario metadata, fetch a bounded buffer, calculate selected-period metrics, and update the URL when callback crosses a period boundary. `FE-33` must not edit Workspace to force integration while `FE-32` owns it. Both may implement against this frozen interface concurrently; `INT-23` joins imports/props and shared CSS serially after both writers complete. If the current types make this exact separation impossible, workers report the smallest required contract change; root makes a one-file ownership amendment, never concurrent editing.

## 4. New bounded packets and genuine parallelism

New IDs: `FE-32` compact rows/typed weather/precise conflict markers; `FE-33` horizon navigation, bounded window fetch, URL/metrics; `INT-23` root integration and shared visual polish. No new backend task is assumed: `/schedule` already has ranged query, weather observations, explicit unavailability, and per-day capacity. A genuinely missing API field requires a separate bounded contract decision, not invented client data.

Start **FE-32 and FE-33 together** as two writing subagents after the root reserves disjoint files. FE-32 owns Workspace, Timeline block/legend, schedule adapter/types/placement, and a **new component-scoped** density CSS file. FE-33 owns Toolbar, App, Timeline route/search schema/schedule query, a **new** horizon helper and component-scoped navigation CSS file. Neither edits `frontend/src/styles.css`, global tokens, generated OpenAPI, tests, backend, `.env`, seed, or the other's files. Root uses the third available slot for read-only diff/contract review while both run. Do not `spawn → wait → spawn`. If one finishes first, review it while the other continues; no third writer. Then root alone performs `INT-23`: resolve interface imports, small shared CSS/z-index/toolbar integration in `styles.css`, and source-trace the entire range/marker flow. This is real parallel implementation, with serial integration only where shared files demand it.

Development-only gate follows [README §4.8](README.md#48-development-first-acceptance-override-2026-10-16): no unit/component/API/E2E test writing or running, browser walkthrough, DB reset, model call, commit, push, deploy, or cloud mutation. Root can run `npm run api:check`, build/lint, and `git diff --check` after both writers finish. Browser E2E/visual QA is later and must explicitly exercise 1366×768 plus mobile: one-booking row height, two concurrent bookings, `+N`, multi-issue day, tooltip focus/Escape, weather location scope, precise overflow day, pan across Oct→Nov and Dec→Jan, month picker, direct link/back-forward, stable metrics, and sticky rail/header/legend. Do not call this production-ready before that QA.
